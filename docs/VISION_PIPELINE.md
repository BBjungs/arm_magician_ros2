# Vision pipeline

The default round detector finds closed edges across the RGB channels and compares each contour's area with the area of its smallest enclosing circle. Targets must cover at least 650 square pixels and fill at least 85% of that circle. Nested edges of an accepted target produce a single detection. With fresh, registered depth, the detector also checks round depth edges. This can recover a raised disk with weak RGB contrast when its center is closer than the surrounding background. The default minimum depth step is 0.01 m (`depth_edge_m`). Missing depth samples do not define an edge. The reported depth is the median valid depth near the center. A ball and a flat disk can both have a circular outline. Set `backend: hsv` in `vision.yaml` to select the color detector.

The operator locks a target with an ROI containing exactly one detected center. The dashboard also turns an explicit list choice into an ROI. The server traces that selection through recent intervening observations, then tracks using centroid displacement, area ratio, and hue. Zero or multiple plausible matches invalidate the track. A lost track requires explicit selection again. Identical objects that exchange places below the camera's sampling resolution cannot be reliably distinguished by this appearance tracker. Inspect the intended workpiece and scene before any future hardware use.

The receiver checks configured dimensions, color optical frame, CameraInfo intrinsics, timestamp skew and freshness. It treats registered `16UC1` as mm and `32FC1` as metres. It samples the scene for depth coverage and checks the median around the target center with a minimum valid sample fraction. Depth gates motion. The control law consumes only pixel error. All thresholds and topic names are in `camera.yaml`, `vision.yaml` and `safety.yaml`.

The live receiver chooses the newest queued RGB header with both a fresh registered depth frame and matching valid color CameraInfo. Header comparisons use integer nanoseconds. A selected frame retires earlier RGB headers. Newer pending frames remain eligible, and are checked again on later ticks. When only CameraInfo is missing or outside tolerance, allow 125 ms from RGB callback entry before releasing a preview. While the previous complete observation from the same source generation is still fresh, defer that preview and continue checking for a complete triplet. Each observation retains its original capture and receive times. The application queues hold 8 RGB, 8 depth and 12 calibration samples. The status field `camera_queue_overflow` counts local queue evictions, including normal turnover of depth and calibration history. These counters do not measure DDS packet loss. When no complete triplet exists, only the oldest eligible RGB preview is released per evaluation so newer frames can still receive their partners.

In live monitoring, loss of registered depth while RGB is still fresh moves a locked target to PENDING REVALIDATION for up to one camera freshness interval. No active target, depth or servo error is exposed while waiting. A unique matching detection with new valid target depth and the same control lease restores the lock. Expiry, ambiguity or invalidated camera identity requires a new selection.

On the Jetson, source the Jazzy and workspace overlays and run `python3 scripts/diagnose-rgbd-timing.py` in the dashboard ROS domain with the same RMW implementation. It samples the three sensor topics for 30 seconds and prints the temporary JSONL path and summary. Arrival records contain ROS header time and observer receipt time; match records contain header and arrival offsets. Percentages are reported against all RGB arrivals and against evaluated RGB frames. Queue counters describe this observer, not DDS packet loss. It stores no pixels and performs no live identity-service or per-pixel depth coverage checks, so a timing match alone does not establish readiness for motion.

The live dashboard exposes a bounded history of 2048 receiver events at GET /api/camera-trace. Poll during a timing capture and deduplicate by sequence number within the process. Repeated evaluations with the same RGB header show retries. Signed skew is in header nanoseconds and callback entry times are monotonic seconds. Local capacity eviction is identified by the evicted header.

Read GET /api/camera-callback-health twice to diagnose an offline receiver. Per-topic raw counts advance at callback entry. Validated counts advance after identity, geometry, freshness, and supported metadata checks, before image decoding. For RGB this also requires a header newer than the retired frame. Rejected messages have reason counters. Unexpected callback exceptions have a separate count and last failure. Enqueued counts describe incoming samples retained by the application queue. CameraInfo duplicates and incoming samples discarded at capacity are counted separately. The callback rate covers the last five seconds (or elapsed time since startup). An RMW receive-to-callback interval includes scheduling and message take/deserialization and is unavailable when the middleware supplies no usable receive timestamp. The executor tick interval and tick age are measured with the monotonic clock. This endpoint queries graph metadata and exposes no image payloads.
